# Shared Document Facts and Projection Boundaries

**Status:** Accepted

**Date:** 2026-09-12

Footnote keeps checked-in repository files and their Git history as the canonical source. The smallest compatibility contract justified by the current repository is a repository identity plus a normalized repository-relative source path, with an optional exact revision only when a consumer actually reads or builds that revision. Projection-specific selection, lifecycle, routing, transport, indexing, and authority policy remain outside that contract.

## Minimum compatibility contract

The current repository justifies these shared semantics:

1. **Repository identity** identifies the repository being discussed or sourced.
2. **Repository-relative path** identifies a file within that repository and uses normalized POSIX separators.
3. **Exact revision, when present,** means the consumer actually read or built content from that revision. An absent revision means the consumer must not claim exact revision provenance.

These facts may continue to travel inside existing contracts such as project-context metadata, TrustGraph document metadata, and generated wiki frontmatter. A new universal `Document` object, shared allowlist, or generalized metadata framework is not justified by the current duplication.

The canonical source remains the checked-in repository and Git history. The existing project-context repository constant is the backend's current canonical slug for Footnote-owned runtime routing; public wiki and external integration code may derive their own URL or URI representation without taking on project-context policy.

## Projection boundaries

The following remain deliberately independent:

- public wiki eligibility and publication lifecycle;
- runtime `project_context` eligibility, categories, priorities, and retrieval limits;
- DeepWiki entrypoints, notes, and vendor limits;
- TrustGraph ingestion, target selection, and external workspace policy;
- GitHub metadata sections and exact-object retrieval;
- bounded source retrieval under [#539](https://github.com/footnote-ai/footnote/issues/539); and
- any future machine-readable or MCP projection.

MCP, if later adopted, is a transport over approved projections. It is not a document authority, retrieval policy, or internal knowledge store. Public documentation metadata also cannot override backend retrieval, provenance, privacy, or authority decisions.

## Consequences

Downstream work should first reuse repository identity, source path, and verified revision evidence, then apply its own eligibility and transport policy. The machine-readable documentation work in [#652](https://github.com/footnote-ai/footnote/issues/652) should project the wiki's public selection and metadata without changing runtime project context. Source retrieval in #539 can use the same source identity vocabulary while remaining independently bounded and access-controlled.

If future duplication proves that a shared runtime helper is needed, it should be introduced at the narrowest existing seam and contain only these facts. This decision does not authorize speculative metadata infrastructure or a cross-projection allowlist.
